# x86 Assembly Kernel

If you are looking for clean APIs and high-level comfort, this is probably the wrong place.

If you want to see what the CPU is actually doing — instruction by instruction — welcome.

A small 32-bit operating system written entirely in NASM assembly. 
- No libc. No runtime. No magic layers. 
- Just boot sectors, interrupts, paging, assembly, and a questionable amount of stubbornness.

Built from scratch on Linux.

## Features

- BIOS boot → protected mode → paging → higher-half kernel (`0xC0100000`)
- USB boot support via LBA (`int 13h AH=42h`)
- GRUB Multiboot v1 support
- Login system (`root` / `deadbeef`)
- Preemptive round-robin scheduler using IRQ0/PIT (100 Hz)
- VGA text shell with history, editing, and tab completion
- In-kernel filesystem with `touch`, `write`, `rm`, `mkdir`, `cp`, `mv`
- Persistent storage across reboots and kernel rebuilds
- Linux-style `int 0x80` syscall interface (50 syscalls)
- User programs assembled into `/bin`
- Graphics modes:
  - 800x600 VBE graphics
  - VGA mode 13h (`320x200x256`)
  - Pixel drawing commands
  - Return to text mode with `F5`

No frameworks were harmed during development.

Several CPU registers were.

## Boot methods

# The kernel supports:

- Custom BIOS bootloader
- GRUB Multiboot v1
- QEMU Multiboot loading

Examples:

# Custom bootloader
```
qemu-system-i386 -drive format=raw,file=os.img,if=ide -m 128
```

# GRUB boot
```
qemu-system-i386 -cdrom grub.iso -boot d \
                 -drive format=raw,file=os.img,if=ide -m 128
```
# Direct Multiboot loading
```
qemu-system-i386 -kernel kernel.bin \
                 -drive format=raw,file=os.img,if=ide -m 128
```
# USB boot
The image can be written directly to a USB drive:
```
sudo dd if=os.img of=/dev/sdX bs=1M conv=fsync status=progress
```

- Replace /dev/sdX carefully. Your future self will thank you.
- Boot using Legacy BIOS / CSM mode. This is a BIOS kernel, not UEFI.
- The bootloader uses BIOS LBA reads (int 13h)
   and checks firmware support before loading. 
- If the BIOS cannot cooperate, 
  the kernel politely complains instead 
  of silently exploding.


## Boot from GRUB (Multiboot)

The kernel includes a Multiboot v1 header, so GRUB can load `kernel.bin` directly.

`bootloader.asm` is optional — both boot paths use the same kernel binary. 

When started by GRUB, the kernel installs its own GDT.

(because GRUB's segment setup is different.)

Test with:

```
make grub-run
```

## Requires:

- grub-mkrescue
- xorriso
- mtools
- grub-pc-bin

# Add it to your machine's GRUB menu:

- sudo cp kernel.bin /boot/mykernel.bin
- sudo update-grub

Example entry:

```
menuentry "x86 DEADBEEF OS" {
    multiboot /boot/mykernel.bin
    boot
}
```

Works on BIOS and UEFI systems with CSM/Legacy enabled.

Pure UEFI is not supported because the kernel uses VGA text memory (0xB8000). 
Also, filesystem persistence is tied to the disk image it boots from.

- Create:

## Requirements:

- 32-bit flat binary (`[bits 32]`, `[org 0x00000000]`)
- End with `ret`
- Use `int 0x80` for kernel services
- Add the name to `COMMANDS` in the `Makefile`

Then:

# make

The program appears as:

/bin/myprogram

Programs are limited to 4 KB. Tiny programs, tiny problems.

# Syscalls

User programs communicate with the kernel through:

- int 0x80

# Calling convention:

- eax = syscall number
- ebx/ecx/edx/esi/edi = arguments
- eax = return value

# Available syscall groups:

- Console output
- Keyboard and timing
- Filesystem operations
- Memory management
- Process control
- Graphics
- Debugging tools

Syscalls execute through interrupt gates, 

with interrupts disabled during handling.

## Persistence

Runtime-created files are stored in:

- RAM (active filesystem state)
- Fixed disk slots (persistent storage)

Each slot has a permanent location, so files survive:

- Reboots
- Kernel rebuilds
- Minor chaos

Build-time files (`/proc`, `/etc`, `/var/log`) 
are embedded into the kernel image and reset on rebuild. 
Runtime-created files use the persistent storage area.

The build system preserves the filesystem region while rebuilding, 
so your carefully created files do not disappear into the void.

## Known limitations

This is a learning kernel, not a production OS.

- Ring 0 only — no user/kernel memory protection (poke the kernel)
- Programs can crash the kernel 
- Files limited to 2048 bytes
- 32 persistent runtime file slots
- Keyboard uses IRQ buffering; disk access is PIO based
- No modern drivers. 
  (because apparently writing drivers is how hobbies escalate)

# Design Philosophy

## Zero Abstraction

If the code does not exist, the feature does not exist.

## Hardware First

The kernel is built around the CPU and hardware itself, 
not layers of libraries and frameworks.

---

# Why This Exists

Modern operating systems hide most of the machine behind abstractions.

This project removes those layers to explore what is actually happening underneath.

The goal is understanding:

- How interrupts work
- How paging works
- How context switching happens
- How hardware is controlled directly
- How operating systems are built from the ground up

Also:

Because making a CPU do things the hard way is fun.
